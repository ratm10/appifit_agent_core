소비자 앱이 REST를 호출하면 Dio 인터셉터가 유효 토큰을 확보해 Bearer 헤더를 붙인다. 토큰은 메모리 → SecureStorage → 신규 발급 3단계로 얻으며, 401이 몰려도 동일 매장 발급은 정확히 1회로 직렬화된다. 상세 구조는 TokenManager L4.
전제 AppFitConfig.configure(환경)→ DioProvider(tokenManager, authProvider)→ 앱이 REST 요청
1
요청 인터셉트
_AppFitAuthInterceptor.onRequest
/auth/가 아니면 shopCode를 6단 폴백(extra→헤더→쿼리→body→경로→authProvider.currentStoreId)으로 확보하고, password는 authProvider → SecureStorage 순으로 복원한다.
shopCode 6단 폴백password 복원

유효 토큰 확보
TokenManager.getValidToken
3단계로 토큰을 얻는다. 각 단계는 shopCode 일치 + 미만료일 때만 hit — 매장이 다르면 그 자리에서 폐기한다.

sign-in API 호출

3
발급 직렬화
_refreshingFuture
동시에 여러 요청이 만료 토큰으로 도착해도 동일 shopCode 발급은 1회. 진행 중 발급의 매장이 다르면 합류하지 않고 완료를 기다린 뒤 자기 매장으로 재평가한다 — 남의 매장 토큰 오수신 방지.
동일 shopCode → 합류다른 shopCode → 대기 후 재평가
4
신규 발급 · 서명
Core REST API
POST /v0/auth/sign-in {id, password}로 TokenInfo를 받아 shopCode 바인딩 후 캐시·저장. API Key 검증은 CryptoUtils HMAC-SHA512 서명을 Waldlust-Signature에 실어 보낸다.
/v0/auth/sign-inHMAC-SHA512 서명만료 isExpiringSoon 1h
5
401 → 재발급 재시도
onError · 1회 제한
응답이 401이면 clearToken → getValidToken 재발급 → _appfit_retried=true 마킹 후 dio.fetch로 1회 재시도. 재시도 후에도 401이면 그대로 전파(무한 루프 차단). password 없으면 재로그인 필요.
clearToken_appfit_retried 1회password 없으면 중단
DioProvider L4 →
이 흐름의 핵심: 토큰 확보는 캐시 우선 3단계로 네트워크를 아끼고, shopCode 격리로 매장 전환 시 남의 토큰이 절대 새지 않으며, 동시 401 폭주는 _refreshingFuture 직렬화 + 요청당 _appfit_retried 1회 제한으로 실제 로그인 API를 한 번만 때린다.
